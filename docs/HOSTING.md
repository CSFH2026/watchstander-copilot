# Hosting

One config file picks where the copilot runs and which model fills each slot.
Both targets answer the same API in [CONTRACTS.md](CONTRACTS.md), so the UI works with either.

| Preset | Target | Models | Offline | Use it for |
| --- | --- | --- | --- | --- |
| `config/local.yaml` | FastAPI on the laptop | fastembed bge-small, on the laptop | Yes | The judged demo. This is the default. |
| `config/cloudflare.yaml` | Pages Functions, D1, Vectorize, Workers AI | Workers AI bge-small | No | Frontend work and teammates without the laptop setup. Never the demo. |

Pick a preset with `WSC_CONFIG`, or copy one and edit it.

## Commands

```bash
make run                                       # local target: offline demo on 127.0.0.1:8000
WSC_CONFIG=config/cloudflare.yaml make run     # cloud backend on this machine, port 8788
WSC_CONFIG=config/cloudflare.yaml make deploy  # D1 migrations, then the Pages deploy
```

The cloud `make run` uses a local D1 database and the real Workers AI models, so it needs wifi and a `wrangler login`.
Test there first.
`make deploy` is the only command that changes anything on Cloudflare.

## The config file

| Key | Values | Notes |
| --- | --- | --- |
| `target` | `local`, `cloudflare` | Where the API runs. |
| `models.embed` | `local`, `cloudflare` | Required. A local target may use `cloudflare` to test with cloud vectors; it is then not offline. |
| `models.transcribe`, `rewrite`, `rerank` | `off` for now | The slots exist. Their providers come with issues 21 and 7. |
| `retrieval.*` | numbers | Tuned per embed model. Rerun the off-topic test after any change. |
| `local.*` | host, port | Used by the local target. |
| `cloudflare.*` | Pages project, D1 name | Used by the cloud target. An empty `account_id` means the account wrangler is logged in to. |

The loader refuses a file that cannot work, and names the key to fix.
A cloud target cannot use a `local` model, because a Worker cannot reach a laptop.

## Datasets

A dataset is one folder under `corpus/` with a `dataset.yaml`.
The config's `dataset:` names the folder, and `WSC_DATASET` overrides it for one run.

| Dataset | Kind | Size | Notes |
| --- | --- | --- | --- |
| `wikihow` | stand-in | 2,437 lists, 14,438 steps | The default. Generated by `scripts/import_wikihow.py`. CC BY-NC-SA 3.0. |
| `ddg` | doctrine | 3 procedures, 27 steps | SSDG casualties from COMSCINST 3541.6A. Has the danger steps. |

```bash
WSC_DATASET=ddg make run                                     # laptop, doctrine
WSC_CONFIG=config/cloudflare.yaml WSC_DATASET=ddg make run   # cloud backend on this machine, doctrine
```

To add a dataset, such as one ship class:

1. Make `corpus/<name>/` and put one procedure file per casualty in it, in the format in [CONTRACTS.md](CONTRACTS.md).
2. Add `corpus/<name>/dataset.yaml` with `title`, `kind` (`doctrine` or `stand-in`), `source`, `license`, and three `examples`.
3. Optionally add `scope.yaml` (equipment covered and not covered) and `abbreviations.yaml` (shorthand) in the same folder.
4. Run the dataset's questions and refusals, then set `retrieval.local.min_cosine` and `retrieval.cloudflare.min_cosine` in `dataset.yaml` between them.

`dataset.yaml` floors override the preset's, because the scores depend on both the text and the model.
A stand-in dataset puts "STAND-IN DATA … not Navy doctrine" at the front of the banner on every page.

The first laptop run on a new dataset builds its index: about 4 minutes for wikiHow.
Each dataset keeps its own index file in `api/data/`, so switching back is instant.

On Cloudflare, `make run` and `make deploy` load the dataset into D1 and its step vectors into a Vectorize index named for the dataset and corpus hash.
Both steps are skipped when that exact content is already there.
Embedding wikiHow takes about a minute, and Vectorize then needs about a minute more before every step is searchable.

## Secrets

Secrets never go in the config file.

| Secret | Where | Made by |
| --- | --- | --- |
| Cloud signing keys | `cloud/.keys/` and `cloud/.dev.vars`, both gitignored | `api/.venv/bin/python scripts/keys_cloud.py` |
| Deployed signing keys | Pages secrets `WSC_KEY_<IDENTITY>` | The commands that `scripts/keys_cloud.py` prints |
| `WSC_CF_AI_TOKEN`, `WSC_CF_ACCOUNT_ID` | Your shell | Only for a local target with `models.embed: cloudflare` |

The cloud keys are separate from the laptop keys in `api/data/keys/`.
Keep `cloud/.keys/`: if it is lost, new keys no longer match the deployed secrets, and both must be set again.

## How the cloud backend stays the same as the laptop

- `api/retrieval/export.py` writes the cloud's inputs with the laptop's own parser, search text, BM25 statistics, and scope word lists: a small `bundle.json` compiled into the code, `seed.sql` for D1 (procedures and keyword postings), and `embed.jsonl` (step texts for Vectorize).
- `cloud/src/` holds only the per-question code: tokenize, scope check, BM25 sum, Vectorize lookup, rank fusion, floors, policy, signing, and the audit chain.
- Vectorize returns the 50 nearest steps with exact scores. The laptop ranks every step, so on a dataset over 50 steps the fused ranks can differ slightly; the floors and the tests are set on each target's own scores.
- Step vectors are written at deploy time through `POST /api/admin/embed`, which accepts only requests signed by the node key in `cloud/.keys/`.
- `WSC_BASE_URL=http://127.0.0.1:8788 make test` runs the same contract tests against the cloud backend.
- `api/.venv/bin/python scripts/cloud_audit.py` exports the cloud audit table and checks it with the laptop verifier. Add `--remote` for the deployed database.
