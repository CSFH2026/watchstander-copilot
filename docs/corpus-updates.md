# Corpus Update Guide

This guide is for maintainers who add or update formal source publications for the DDG corpus. It explains the current workflow in the repository. It does not create a new approval process, automatic PDF importer, automatic revision archive, or historical audit binding.

The short version:

1. Keep the original publication outside the active corpus.
2. Record where it came from and which revision it is.
3. Edit the DDG YAML extracts in `corpus/ddg/src/`.
4. Regenerate the procedure Markdown with `scripts/build_ddg.py`.
5. Rebuild the SQLite search index with `make index` or the Windows command below.
6. Check the generated procedures, step order, cautions, and citations against the source.

## What Each Layer Means

The DDG workflow has four layers:

| Layer | Location | Maintainer action |
| --- | --- | --- |
| Original publications | Outside git, usually `watchstander-copilot-data/raw/` or the team USB copy | Keep downloaded originals and notes here. Do not commit large raw publications. |
| Source registry | `corpus/ddg/src/sources.yaml` | Add or update small citation records used by extracts. |
| YAML extracts | `corpus/ddg/src/*.yaml` | Edit these by hand. They hold transcribed source text, tiers, symptoms, causes, effects, and ordered steps. |
| Generated Markdown | `corpus/ddg/EOCC-*.md` | Generated by `scripts/build_ddg.py`. Do not edit these directly. |
| Search index | `api/data/index.sqlite` | Generated locally by `make index`; it is a runtime artifact, not a source file. |

The project does not import arbitrary PDFs automatically. A maintainer reads the publication, records the source, transcribes the relevant passages into an extract, writes or revises the procedure steps, and then runs the generator.

## Source Record Template

Copy this template into the relevant source documentation when adding or updating a publication. If a value is unknown, write `unknown` instead of leaving it blank.

```markdown
### <Publication short name or registry key>

- Publication identity: <title, issuing organization, document number>
- Revision: <revision, change number, edition, or unknown>
- Publication date: <date or unknown>
- Effective date: <date or unknown>
- Provenance URL: <URL or unknown>
- Retrieval date: <YYYY-MM-DD>
- Archived-file location: <outside-git path, for example watchstander-copilot-data/raw/<folder>/<file>>
- SHA-256 checksum: <checksum of the archived file or unknown>
- Affected procedures: <procedure IDs or unknown>
- Superseded revision: <registry key, document revision, commit, or unknown>
- Review status: <draft | source checked | procedure checked | team reviewed | unknown>
```

Use PowerShell to compute a checksum:

```powershell
Get-FileHash -Algorithm SHA256 C:\path\to\publication.pdf
```

Use Git Bash, macOS, or Linux:

```bash
sha256sum /path/to/publication.pdf
```

## Add Or Update A Publication

1. Prepare the local tools once.

   Standard command:

   ```bash
   make setup
   ```

   Windows PowerShell equivalent when `make` is not installed:

   ```powershell
   python -m venv .venv
   .\.venv\Scripts\python.exe -m pip install -q --upgrade pip
   .\.venv\Scripts\python.exe -m pip install -q -r .\api\requirements.txt
   Push-Location ui
   npm install
   Pop-Location
   $env:WSC_DATASET = "ddg"
   Push-Location api
   ..\.venv\Scripts\python.exe -m retrieval.indexer
   Pop-Location
   Remove-Item Env:\WSC_DATASET
   git config core.hooksPath .githooks
   ```

   This setup may need network access the first time. After the model cache is present, the local demo should run without network.

2. Start from the newest `origin/main` on an issue branch.

   ```bash
   git fetch origin
   git switch -c 79-corpus-updates-guide origin/main
   ```

   PowerShell uses the same Git commands:

   ```powershell
   git fetch origin
   git switch -c 79-corpus-updates-guide origin/main
   ```

3. Save the original publication outside git.

   Use a stable folder name such as `watchstander-copilot-data/raw/navedtra-14114-gse-gsm-vol2-rev-a/`. Keep older publication files there or on the team USB copy, not under `corpus/ddg/`.

4. Add a source record.

   Update `docs/data-sources.md` or another team source note with the template above. Include the checksum, retrieval date, and archived-file location. If the new publication supersedes an earlier edition, name the older edition and the Git commit that last contained extracts based on it.

5. Update `corpus/ddg/src/sources.yaml`.

   Add a distinct registry key for a new edition. Do not reuse a key when the citation should point to a different revision. For example, prefer `N14114_CH1` or another clear revision-specific key over silently changing `N14114`.

   Each registry entry needs:

   ```yaml
   N14114:
     short: "NAVEDTRA 14114 ch {at}"
     cite: NAVEDTRA 14114 Gas Turbine Systems Technician (Electrical) 3/(Mechanical) 3, Volume 2 (Distribution Statement A)
     locator: chapter
     url: https://www.militarynewbie.com/wp-content/uploads/2013/11/NAVEDTRA-14114-Gas-Turbine-Systems-Technician-Volume-2.pdf
   ```

6. Edit the YAML extract, not the generated Markdown.

   The extract files under `corpus/ddg/src/` contain:

   - `group`: the system name used in generated front matter.
   - `procedures`: one list item per procedure.
   - `id`: stable procedure ID, such as `EOCC-SSGTG-LLOP`.
   - `tier`: `taken`, `adapted`, or `pattern`.
   - `sources`: registry refs plus locator, title, and transcribed source text.
   - `synthetic`: required for `adapted` procedures; names steps not directly from a source.
   - `symptoms`, `causes`, `effects`, `associated`: searchable procedure metadata.
   - `steps`: ordered steps with optional `requires` and `danger`.

   Keep source text exact enough to verify the citation. Keep adapted or synthetic material clearly labeled in `tier`, `synthetic`, `note`, and `status` output.

7. Preserve earlier revisions manually.

   The current workflow does not automatically retain publication revisions. Use these conventions:

   - Keep older original files outside the active corpus.
   - Keep source records for older revisions in `docs/data-sources.md` or the team source notes.
   - Reference Git commits that contain earlier YAML extracts.
   - Do not index archived copies alongside current procedures.
   - Do not commit large raw publications.

8. Regenerate generated procedure Markdown.

   Standard command:

   ```bash
   .venv/bin/python scripts/build_ddg.py
   ```

   Windows PowerShell equivalent:

   ```powershell
   .\.venv\Scripts\python.exe .\scripts\build_ddg.py
   ```

   The generator can delete retired `EOCC-*.md` outputs that no longer appear in the extracts. It also assigns step IDs from the current step order, so moving steps can renumber step IDs. Check those diffs carefully.

9. Check generated files are current.

   Standard command:

   ```bash
   .venv/bin/python scripts/build_ddg.py --check
   ```

   Windows PowerShell equivalent:

   ```powershell
   .\.venv\Scripts\python.exe .\scripts\build_ddg.py --check
   ```

10. Rebuild the search index.

   Standard command:

   ```bash
   make index DATASET=ddg
   ```

   Windows PowerShell equivalent:

   ```powershell
   $env:WSC_DATASET = "ddg"
   Push-Location api
   ..\.venv\Scripts\python.exe -m retrieval.indexer
   Pop-Location
   Remove-Item Env:\WSC_DATASET
   ```

   `api/data/index.sqlite` is generated locally. Do not commit it.

11. Restart the app after rebuilding the index.

   Standard command:

   ```bash
   make demo DATASET=ddg
   ```

   Windows PowerShell equivalent:

   ```powershell
   $env:WSC_DATASET = "ddg"
   Push-Location ui
   npm run build
   Pop-Location
   Push-Location api
   $env:HF_HUB_OFFLINE = "1"
   ..\.venv\Scripts\uvicorn.exe main:app --host 127.0.0.1 --port 8000
   Pop-Location
   ```

   Leave `HF_HUB_OFFLINE=1` when you are proving the local demo does not need the network. Do not claim Wi-Fi-off testing unless Wi-Fi was actually disabled.

## Verify Procedures And Citations

Use a disposable copy or the existing extracts with `--check` when you are validating commands. Do not change real corpus content just to test commands.

1. Confirm generated files match extracts:

   ```powershell
   .\.venv\Scripts\python.exe .\scripts\build_ddg.py --check
   ```

2. Rebuild the index after real corpus changes:

   ```powershell
   $env:WSC_DATASET = "ddg"
   Push-Location api
   ..\.venv\Scripts\python.exe -m retrieval.indexer
   Pop-Location
   Remove-Item Env:\WSC_DATASET
   ```

3. Run the focused DDG corpus checks:

   Standard command:

   ```bash
   .venv/bin/python -m pytest tests/test_dataset_ddg.py -q
   ```

   Windows PowerShell equivalent:

   ```powershell
   .\.venv\Scripts\python.exe -m pytest tests\test_dataset_ddg.py -q
   ```

4. Run the full Python test suite when practical:

   Standard command:

   ```bash
   make test
   ```

   Windows PowerShell equivalent:

   ```powershell
   .\.venv\Scripts\python.exe -m pytest tests -q
   ```

5. Verify the audit log only when your validation intentionally touches audit behavior:

   Standard command:

   ```bash
   make verify
   ```

   Windows PowerShell equivalent:

   ```powershell
   Push-Location api
   ..\.venv\Scripts\python.exe -m trust.verify ..\audit\log.jsonl
   Pop-Location
   ```

6. Check actual procedures by hand:

   - Open each changed `corpus/ddg/EOCC-*.md`.
   - Check the `source` line points to the intended registry entry, locator, title, and URL.
   - Check `tier` and `status` explain whether steps are taken, adapted, or synthetic.
   - Check every step appears in the intended order.
   - Check each `requires:` points only to valid earlier steps unless the generated policy intentionally allows a separate first action.
   - Check each `danger:` warning matches a real source concern or clearly documented project adaptation.
   - Compare the transcribed `sources[].text` in the YAML extract against the original publication.

7. Keep audit validation isolated.

   The current audit log does not bind historical entries to a specific publication revision. Preserve existing `audit/log.jsonl`. If you need to test audit behavior, use a disposable log path or a copy, then delete the disposable file.

## Common Failures

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| YAML parser error | Indentation, missing colon, bad quote, or list item in `corpus/ddg/src/*.yaml` | Fix the YAML around the reported line. Keep multiline source text under `text: >-`. |
| `unknown source ref` | An extract cites a `ref` that is not in `sources.yaml` | Add the revision-specific registry key or correct the `ref`. |
| `defined twice` | Two extracts use the same `id` | Keep one stable procedure ID or rename the new procedure deliberately. |
| `requires ... not an earlier step` | A step requires itself, a later step, or a typo | Fix the `requires` list in the extract. |
| `associated ... is not a procedure` | `associated` names a missing or retired procedure | Update or remove the association. |
| `generated files are stale` | Extracts changed but Markdown was not regenerated | Run `scripts/build_ddg.py`, then review the Markdown diff. |
| `front matter is missing ...` | A generated or hand-written Markdown file lacks required contract fields | Fix the extract and regenerate. Do not patch generated Markdown by hand. |
| Duplicate IDs while indexing | Two Markdown files declare the same `procedure_id` | Fix the extracts and regenerate. |
| Wrong dataset in tests or demo | `WSC_DATASET` or config selects `wikihow` or another dataset | Set `DATASET=ddg` for `make`, or `$env:WSC_DATASET = "ddg"` in PowerShell. |
| Model unavailable | The embedding model is not cached locally | Run setup when network is allowed, or restore `api/models/` from the team USB cache. |
| Incorrect citations | Registry key, locator, title, URL, or transcribed text points to the wrong revision | Add a revision-specific registry key and update the extract citation. |

## Boundaries To Keep Clear

- Project review is not formal approval of a source publication.
- Approved procedure text is authoritative; do not invent missing steps.
- The DDG corpus includes adapted and synthetic training material. Keep those labels visible.
- The current workflow does not automatically retain publication revisions.
- The current audit chain records procedure and step IDs, but it does not bind old audit entries to a publication revision.
- Archived publications and older extracts are manual records, not active indexed corpus content.
